5.1 Servidor logico
--------------------------------------------------------------
El servidor se creo desde el portal de Azure porque las regiones
East US y West US 2 no aceptaban servidores SQL nuevos para esta
suscripcion. La region que si acepto fue Central US.

Datos utilizados:
  Nombre    : sql-pacientes-matias-26
  Region    : Central US
  Usuario   : adminsql
  Password  : <CONTRASENA_ADMIN_SQL>
  Firewall  : "Permitir que los servicios de Azure accedan" = Si

Comando equivalente por CLI:

az sql server create --name sql-pacientes-matias-26 --resource-group rg-pacientes-aa --location centralus --admin-user adminsql --admin-password <CONTRASENA_ADMIN_SQL>


5.2 Bases de datos
--------------------------------------------------------------

az sql db create --resource-group rg-pacientes-aa --server sql-pacientes-matias-26 --name PacientesDB --service-objective Basic --backup-storage-redundancy Local

az sql db create --resource-group rg-pacientes-aa --server sql-pacientes-matias-26 --name HistorialDB --service-objective Basic --backup-storage-redundancy Local


5.3 Reglas de firewall
--------------------------------------------------------------
Necesarias para ejecutar los scripts desde SQL Server Management
Studio. La IP publica cambia al cambiar de red, por lo que se
crea una regla por cada ubicacion desde la que se trabaja.

curl ifconfig.me

az sql server firewall-rule create --resource-group rg-pacientes-aa --server sql-pacientes-matias-26 --name MiPC --start-ip-address <IP_PUBLICA> --end-ip-address <IP_PUBLICA>


5.4 Creacion de las tablas
--------------------------------------------------------------
Los scripts BaseDatos/Azure_PacientesDB.sql y
BaseDatos/Azure_HistorialClinicoDB.sql se ejecutaron desde SSMS,
seleccionando previamente la base correspondiente en el
desplegable de la barra de herramientas.

En Azure SQL no se admite CREATE DATABASE ni USE dentro de un
script: cada conexion esta atada a una sola base.


5.5 Usuarios dedicados por base de datos
--------------------------------------------------------------
En lugar de que los microservicios se conecten con el
administrador del servidor, cada uno tiene su propio usuario con
permisos de lectura y escritura unicamente sobre su base.
Es el principio de minimo privilegio.

Ejecutado en SSMS, conectado a Azure y con PacientesDB
seleccionada:

  CREATE USER usuario_pacientes WITH PASSWORD = '<CONTRASENA_USUARIO_PACIENTES>';
  GO
  ALTER ROLE db_datareader ADD MEMBER usuario_pacientes;
  GO
  ALTER ROLE db_datawriter ADD MEMBER usuario_pacientes;
  GO

Con HistorialDB seleccionada:

  CREATE USER usuario_historialclinico WITH PASSWORD = '<CONTRASENA_USUARIO_HISTORIAL>';
  GO
  ALTER ROLE db_datareader ADD MEMBER usuario_historialclinico;
  GO
  ALTER ROLE db_datawriter ADD MEMBER usuario_historialclinico;
  GO

Nota: son usuarios contenidos, propios de Azure SQL. Viven solo
dentro de su base y no existen a nivel de servidor, por lo que
no aparecen en Security > Logins.

Para la ejecucion local en Docker Compose se crearon los mismos
usuarios en SQL Server, pero con el metodo clasico (login de
servidor + usuario de base), porque SQL Server local no habilita
usuarios contenidos por defecto:

  CREATE LOGIN usuario_pacientes WITH PASSWORD = '<CONTRASENA>', CHECK_POLICY = OFF;
  GO
  CREATE USER usuario_pacientes FOR LOGIN usuario_pacientes;
  GO
  ALTER ROLE db_datareader ADD MEMBER usuario_pacientes;
  GO
  ALTER ROLE db_datawriter ADD MEMBER usuario_pacientes;
  GO

8.1 RabbitMQ
--------------------------------------------------------------
Ingress interno: accesible solo desde dentro del entorno, para
que la cola no quede expuesta a internet.
Transporte TCP porque AMQP no es HTTP.

az containerapp create --name rabbitmq --resource-group rg-pacientes-aa --environment env-pacientes --image rabbitmq:4-management --target-port 5672 --ingress internal --transport tcp --env-vars RABBITMQ_DEFAULT_USER=<USUARIO_RABBITMQ> RABBITMQ_DEFAULT_PASS=<CONTRASENA_RABBITMQ> --cpu 1.0 --memory 2.0Gi

9. SECRETOS EN CONTAINER APPS
==============================================================
Las cadenas de conexion, la clave JWT y la contrasena de RabbitMQ
se guardan en el almacen de secretos del Container App en lugar
de quedar como variables de entorno en texto plano. La variable
apunta al secreto con la sintaxis secretref:

9.1 Cadenas de conexion a SQL
--------------------------------------------------------------

az containerapp secret set --name pacientes --resource-group rg-pacientes-aa --secrets pacientes-sql="Server=tcp:sql-pacientes-matias-26.database.windows.net,1433;Database=PacientesDB;User ID=usuario_pacientes;Password=<CONTRASENA_USUARIO_PACIENTES>;Encrypt=True;TrustServerCertificate=False;"

az containerapp update --name pacientes --resource-group rg-pacientes-aa --set-env-vars ConnectionStrings__PacientesConnection=secretref:pacientes-sql

az containerapp secret set --name historial --resource-group rg-pacientes-aa --secrets historial-sql="Server=tcp:sql-pacientes-matias-26.database.windows.net,1433;Database=HistorialDB;User ID=usuario_historialclinico;Password=<CONTRASENA_USUARIO_HISTORIAL>;Encrypt=True;TrustServerCertificate=False;"

az containerapp update --name historial --resource-group rg-pacientes-aa --set-env-vars ConnectionStrings__HistorialConnection=secretref:historial-sql


9.2 Contrasena de RabbitMQ
--------------------------------------------------------------

az containerapp secret set --name pacientes --resource-group rg-pacientes-aa --secrets rabbitmq-password=<CONTRASENA_RABBITMQ>
az containerapp update --name pacientes --resource-group rg-pacientes-aa --set-env-vars RabbitMQ__Password=secretref:rabbitmq-password

az containerapp secret set --name historial --resource-group rg-pacientes-aa --secrets rabbitmq-password=<CONTRASENA_RABBITMQ>
az containerapp update --name historial --resource-group rg-pacientes-aa --set-env-vars RabbitMQ__Password=secretref:rabbitmq-password


9.3 Clave JWT
--------------------------------------------------------------
El mismo valor en los tres servicios: si difiere en alguno, el
token emitido por OAuthJWT es rechazado por los microservicios.

az containerapp secret set --name oauthjwt --resource-group rg-pacientes-aa --secrets jwt-key=<CLAVE_JWT>
az containerapp update --name oauthjwt --resource-group rg-pacientes-aa --set-env-vars Jwt__Key=secretref:jwt-key

az containerapp secret set --name pacientes --resource-group rg-pacientes-aa --secrets jwt-key=<CLAVE_JWT>
az containerapp update --name pacientes --resource-group rg-pacientes-aa --set-env-vars Jwt__Key=secretref:jwt-key

az containerapp secret set --name historial --resource-group rg-pacientes-aa --secrets jwt-key=<CLAVE_JWT>
az containerapp update --name historial --resource-group rg-pacientes-aa --set-env-vars Jwt__Key=secretref:jwt-key

10. REPLICA FIJA PARA LA DEMOSTRACION
==============================================================
Por defecto los Container Apps escalan a cero cuando no reciben
peticiones, lo que hace que la primera peticion despues de un
rato tarde mucho. Se fija una replica activa en los cinco.

az containerapp update --name oauthjwt --resource-group rg-pacientes-aa --min-replicas 1 --max-replicas 1
az containerapp update --name pacientes --resource-group rg-pacientes-aa --min-replicas 1 --max-replicas 1
az containerapp update --name historial --resource-group rg-pacientes-aa --min-replicas 1 --max-replicas 1
az containerapp update --name rabbitmq --resource-group rg-pacientes-aa --min-replicas 1 --max-replicas 1
az containerapp update --name apigateway --resource-group rg-pacientes-aa --min-replicas 1 --max-replicas 1

12. VERIFICACION Y PRUEBAS
==============================================================

az containerapp list --resource-group rg-pacientes-aa --output table

az containerapp logs show --name pacientes --resource-group rg-pacientes-aa --tail 50

Pruebas realizadas desde Postman contra el API Gateway:

  1. GET /api/Pacientes sin token          -> 401 Unauthorized
  2. POST /api/Auth/login (admin/1234)     -> devuelve el token
  3. GET /api/Pacientes con token          -> 200 OK
  4. GET /api/HistorialClinico con token   -> 200 OK
  5. POST /api/Pacientes con token         -> 201 Created
  6. GET /api/HistorialClinico             -> el historial del paciente
     recien creado aparece automaticamente, generado por el
     consumidor de RabbitMQ
  7. Token con rol "medico" en un POST     -> 403 Forbidden
