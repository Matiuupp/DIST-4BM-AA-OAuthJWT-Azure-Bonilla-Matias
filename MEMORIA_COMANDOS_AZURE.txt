5. AZURE SQL DATABASE
--------------------------------------------------------------
El servidor logico se creo desde el portal de Azure porque las
regiones East US y West US 2 no aceptaban servidores SQL nuevos
para esta suscripcion. La region que si acepto fue Central US.

Datos utilizados:
  Nombre    : sql-pacientes-matias-26
  Region    : Central US
  Usuario   : adminsql
  Password  : <CONTRASENA_SQL>
  Firewall  : "Permitir que los servicios de Azure accedan" = Si

Comando equivalente por CLI:
az sql server create --name sql-pacientes-matias-26 --resource-group rg-pacientes-aa --location centralus --admin-user adminsql --admin-password <CONTRASENA_SQL>

Creacion de las dos bases:

az sql db create --resource-group rg-pacientes-aa --server sql-pacientes-matias-26 --name PacientesDB --service-objective Basic --backup-storage-redundancy Local

az sql db create --resource-group rg-pacientes-aa --server sql-pacientes-matias-26 --name HistorialDB --service-objective Basic --backup-storage-redundancy Local

Regla de firewall para el equipo local (necesaria para ejecutar
los scripts desde SQL Server Management Studio):

curl ifconfig.me

az sql server firewall-rule create --resource-group rg-pacientes-aa --server sql-pacientes-matias-26 --name MiPC --start-ip-address <IP_PUBLICA> --end-ip-address <IP_PUBLICA>

Los scripts BaseDatos/Azure_PacientesDB.sql y
BaseDatos/Azure_HistorialClinicoDB.sql se ejecutaron desde SSMS,
seleccionando previamente la base correspondiente. En Azure SQL
no se admite USE ni CREATE DATABASE dentro del script.

8.1 RabbitMQ
Ingress interno: solo accesible desde dentro del entorno.
Transporte TCP porque AMQP no es HTTP.

az containerapp create --name rabbitmq --resource-group rg-pacientes-aa --environment env-pacientes --image rabbitmq:4-management --target-port 5672 --ingress internal --transport tcp --env-vars RABBITMQ_DEFAULT_USER=<USUARIO_RABBITMQ> RABBITMQ_DEFAULT_PASS=<CONTRASENA_RABBITMQ> --cpu 1.0 --memory 2.0Gi

9. VERIFICACION Y PRUEBAS
--------------------------------------------------------------

Listado de los servicios desplegados:

az containerapp list --resource-group rg-pacientes-aa --output table

Consulta de logs de un servicio:

az containerapp logs show --name pacientes --resource-group rg-pacientes-aa --tail 50

Pruebas realizadas desde Postman a traves del API Gateway:
  1. GET /api/Pacientes sin token          -> 401 Unauthorized
  2. POST /api/Auth/login (admin/1234)     -> devuelve el token
  3. GET /api/Pacientes con token          -> 200 OK
  4. POST /api/Pacientes con token         -> 201 Created
  5. GET /api/HistorialClinico con token   -> el historial del
     paciente aparece creado automaticamente por RabbitMQ


--------------------------------------------------------------
10. ELIMINACION DE LOS RECURSOS
--------------------------------------------------------------
Al finalizar el periodo de revision se elimina el Resource Group
completo, lo que borra todos los recursos asociados y evita
consumo posterior de creditos.

az group delete --name rg-pacientes-aa --yes --no-wait

Verificacion de que ya no existe:

az group list --output table
