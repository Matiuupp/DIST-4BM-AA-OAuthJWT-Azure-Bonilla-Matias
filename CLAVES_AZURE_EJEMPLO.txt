2. USUARIOS DEDICADOS POR BASE DE DATOS
--------------------------------------------------------------
Cada microservicio se conecta con su propio usuario, que tiene
permisos de lectura y escritura unicamente sobre su base. Es el
principio de minimo privilegio: si un servicio se viera
comprometido, el acceso queda limitado a sus propios datos.

Base PacientesDB
  Usuario       : usuario_pacientes
  Contrasena    : <CONTRASENA_USUARIO_PACIENTES>
  Roles         : db_datareader, db_datawriter

Base HistorialDB
  Usuario       : usuario_historialclinico
  Contrasena    : <CONTRASENA_USUARIO_HISTORIAL>
  Roles         : db_datareader, db_datawriter

Ninguno de los dos puede crear o alterar tablas, ni acceder a
la base del otro microservicio.

--------------------------------------------------------------
3. FORMATO DE LAS CADENAS DE CONEXION
--------------------------------------------------------------

En Azure (Encrypt obligatorio):

Server=tcp:<SERVIDOR>.database.windows.net,1433;
Database=<NOMBRE_BASE>;
User ID=<USUARIO>;
Password=<CONTRASENA>;
Encrypt=True;
TrustServerCertificate=False;

En local con Docker Compose:

Server=host.docker.internal,1433;
Database=<NOMBRE_BASE>;
User Id=<USUARIO>;
Password=<CONTRASENA>;
TrustServerCertificate=True;
Encrypt=False;

Nota: en el docker-compose.yml la cadena va en una sola linea y
entre comillas dobles. El bloque >- de YAML inserta espacios
entre lineas y rompe las contrasenas con caracteres especiales.

5. JWT (servicio OAuthJWT)
--------------------------------------------------------------
Key             : <CLAVE_JWT_SECRETA>
Issuer          : OAuthJWT
Audience        : MicroserviciosPacientes
ExpireMinutes   : 60

Los tres servicios (OAuthJWT, Pacientes.Api e
HistorialClinico.Api) comparten exactamente la misma Key,
Issuer y Audience. OAuthJWT firma el token con esa clave y los
microservicios verifican la firma con la misma. Si alguno de
los tres valores difiere, el token es rechazado aunque sea
legitimo.

Un JWT no es secreto, es firmado: cualquiera puede leer su
contenido, pero nadie puede modificarlo sin conocer la clave.

8. USUARIOS DE PRUEBA DEL SISTEMA
--------------------------------------------------------------
Definidos en el AuthController del servicio OAuthJWT. No son
credenciales de infraestructura sino datos de uso de la
aplicacion, por eso se documentan con sus valores reales para
que puedan probarse los endpoints:

Usuario: admin    Password: 1234    Rol: Administrador
Usuario: medico   Password: 1234    Rol: Usuario

El rol Administrador puede consultar, crear, editar y eliminar.
El rol Usuario solo puede consultar: si intenta crear, recibe
403 Forbidden.

--------------------------------------------------------------
RECOMENDACIONES DE SEGURIDAD
--------------------------------------------------------------
- Las contrasenas combinan mayusculas, minusculas, numeros y
  caracteres especiales.
- Se generaron con un generador de contrasenas y no reutilizan
  contrasenas personales.
- Evitar los caracteres ; y ' en las contrasenas: el punto y
  coma separa los campos de una cadena de conexion.
- No publicar contrasenas reales, JWT Keys ni secretos en un
  repositorio publico.
